# Online migration and consistency verification

## Migration Principles

You cannot move the entire warehouse at once after shutdown. Taking virtual bucket as the smallest unit:

1. Freeze the bucket’s target shard decision and record the migration epoch.
2. Copy the consistent snapshot from the source shard to the target shard.
3. Incremental writes after snapshot capture.
4. After the target shard catch up to the Migration Watermark (migration increment boundary), perform row count, checksum and sampling semantic verification.
5. Turn on Shadow Read and compare source and target results.
6. A small proportion of reads are cut to the target, and writes are still received by a single authoritative shard.
7. Atomic update shard map epoch, switch write ownership.
8. The source shard retains a read-only rollback window and is finally recycled.

## Avoid dangerous double writing

When an application double-writes two shards at the same time, it is easy to cause success on one side and failure on the other. Prefer using the source shard's WAL/CDC replication delta, and always make it clear which shard is the authoritative writer.

## rollback

Read traffic can be restored directly to the source shard before Write Cutover. If the target is abnormal after switching, you must first use Fencing to prevent the target from continuing to write, and then reversely synchronize the increments generated by the target to the source; confirm that the source shard has applied these increments and aligned them with the write watermark of the target before updating the routing epoch. You cannot allow two shards to accept writes at the same time.

## Verification content

- Post/Follow fact row number and checksum;
- Unique constraints and idempotent keys;
- FeedItem / Timeline sorting boundary;
- follow_id with bidirectional index;
- The target shard epoch of the task in the Queue.
