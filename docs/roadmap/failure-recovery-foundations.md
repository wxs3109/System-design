## 基础概念应该覆盖什么

基础知识是独立的学习内容。知识点可以先讲解、再用一个或多个 Lab 验证，并被多个案例引用；不要求先完成综合案例才补基础知识，也不把每个术语都拆成一题。

下表是分布式系统基础的核心分组，引用矩阵已有能力，不代替完整矩阵中的 API、网络、索引、地理系统等专题。入门需要先理解问题、保证和反例；复杂协议的全部实现细节可以逐步深入。

| 知识组 | 应覆盖的基础概念 | 主要回答的问题 | 对应能力 |
|---|---|---|---|
| 故障与正确性 | 局部失败、崩溃/暂停、网络分区、消息延迟/丢失/重复/乱序；超时与结果未知；接收/持久化/处理完成的成功边界；业务不变量、安全性与进展 | 到底知道发生了什么？什么算成功，什么绝不能发生？ | REQ-01 / REQ-02 / API-01 / COORD-01 |
| 容量、分布与过载 | 到达率、处理能力、并发槽、排队、瓶颈；缓存/TTL/淘汰、分片、一致性哈希、hot key；限流、背压、熔断、降级、资源隔离 | 工作为什么积压？怎样保护系统并解释资源取舍？ | PERF-01 / PERF-02 / PERF-04 / SCALE-01 / SCALE-03 / SCALE-04 / MSG-05 / REL-03 |
| 请求可靠性 | Timeout/Deadline、取消与仍在执行的工作；Retry、退避/Jitter、重试预算；Idempotency、去重、幂等键范围/保留期/参数冲突 | 失败或结果未知后，怎样重试而不重复业务效果？ | REL-01 / REL-02 |

| 本地事务与并发正确性 | ACID、原子提交、事务隔离、丢失更新与并发冲突；条件更新/CAS、版本检查、乐观/悲观并发控制 | 没有机器故障时，多个请求为什么仍可能把状态改错？ | DATA-04 / DATA-05 / DATA-06 |

| 复制、一致性与共识 | 副本延迟、旧读、读己之写、强/最终一致性；提交与应用；Leader、Quorum、选举、日志复制与 Raft 基本模型 | 读到哪一版？哪些写算提交？协调者自身失败或网络分区时如何保持约定保证？ | CONS-01 / CONS-02 / CONS-03 / COORD-03 / COORD-04 |
| 跨服务可靠流程 | 双写缺口、Transactional Outbox、发布重试与消费幂等；Saga、Compensation、恢复进度、补偿失败；2PC 的原子提交与阻塞边界 | 一个业务跨多个服务，部分完成后怎样继续或纠正？ | MSG-04 / CONS-04 / OPS-05 |
| 持久性与数据恢复 | 内存与稳定存储、WAL、Checkpoint/Snapshot、日志重放；复制与备份的区别、恢复演练、RPO/RTO | 已确认的结果如何保留？进程恢复和数据恢复有什么区别？ | DATA-06 / REL-04 / REL-05 |

贯穿各组的基础要求：用指标、日志、Trace 和业务状态判断结果（OPS-01）；声明调用方、权限与租户边界（SEC-01 / SEC-02）；讨论版本兼容和变更后的恢复（API-05 / OPS-03 / OPS-04）。这些是讲解和验收维度，不必一开始各造一套课程。

原五个 Lab 覆盖第二组中的限定切片：服务排队、DB 瓶颈、缓存压力、一致性哈希和 Hot Key。六个协议 Lab 覆盖单意图请求重试、ACK/Checkpoint、Outbox、Heartbeat、Lease/Fencing 和 Saga 的限定故障切片；不代表完整数据库事务、broker、复制一致性或共识已经覆盖。

## 知识、Lab、案例如何关联

| 对象 | 职责 | 与其他对象的关系 |
|---|---|---|
| Concept：基础知识 | 解释问题、最小例子、机制、保证与反例；可独立阅读 | 引用相关 Lab 和案例，同一概念只有一个规范讲解入口 |
| Lab：交互实验 | 让用户改变条件、运行模型并核验证据 | 一个 Lab 可覆盖多个概念，例如重试+幂等；不重复维护长篇知识正文 |
| Case：系统设计案例 | 在具体需求和约束下应用、组合概念 | 声明所用概念并链接已有 Lab；案例资料和可作答设计题分别标记状态 |
| Learning Path：学习路径 | 给上述对象安排一种学习顺序 | 只组织引用，不复制知识或题目，也不强制用户按顺序解锁 |

例子：**幂等知识页 ↔ 响应丢失后重试 Lab ↔ 订单创建/视频任务提交案例**；**Heartbeat 知识页 ↔ 暂停与失联 Lab ↔ Worker 故障恢复案例**。案例是应用关联，基础知识与 Lab 本身可以先独立交付。

每个概念讲解统一包含：① 要解决的问题；② 一个最小例子；③ 机制如何工作；④ 保证成立的条件；⑤ 一个失效反例；⑥ 相关实验和案例。前置概念直接链接，不用再堆一页术语列表。

## 先建立框架

每次先问四个问题：**哪里失败了？哪些效果已经发生？什么绝不能发生？恢复后要继续什么？** 再选择机制。

区分两个目标：不重复创建、不漏处理、不接受旧持有者写入等“不能做错”；通信和服务恢复后，任务能继续完成的“能够推进”。超时、重试或一把锁都不能单独保证全部目标。

用同一个小案例贯穿：**提交视频任务 → 保存任务 → 发出转码事件 → Worker 处理 → 发布结果**。只操作有限任务、符号产物和逻辑消息，不上传真实视频、不部署中间件。每次运行只注入一种故障，最后换故障时刻检验理解。

## 故障与恢复的入门路径：六次学习，每次约 30 分钟

以下六讲是一条入门路径，不是上面基础概念范围的全部。并发冲突与过载保护已作为两个独立扩展实验；乱序与永久失败可在消息 Lab 自由模式操作；复制、一致性、持久恢复已有下文所列的进阶实验。每次只要求掌握当前问题所需的概念。

每次按“5 分钟看故障与预测 → 10 分钟运行反例 → 10 分钟调整策略 → 5 分钟解释证据”进行。概念是修复工具，页面标题使用下表中的问题。

| 顺序 / 故障问题 | 对应工具 | 在平台里做什么 | 必须解释的边界 / 能力 ID |
|---|---|---|---|
| 1. 没收到响应，任务到底创建了吗？ | Timeout、有限 Retry、退避、[Idempotency](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) | 分别让请求没到达、任务已创建但响应丢失；比较不重试、直接重试、同一个幂等键重试 | 超时表示结果未知；重试可能重复效果。先用 5 分钟理解本地原子提交，把去重记录、任务创建和返回结果放在同一提交边界。REL-01 / REL-02 / DATA-04 |
| 2. Worker 做到一半崩溃，从哪里继续？ | [ACK](https://www.rabbitmq.com/docs/confirms)、重投、[Checkpoint](https://kafka.apache.org/design/)、幂等处理 | 分别在 ACK 前、业务效果后但进度未提交时崩溃，再从保存状态恢复 | ACK 是对某一交付阶段的确认；checkpoint 记录进度。提前确认可能漏工作，效果与进度之间的空隙可能重做；需要原子效果/进度提交或可安全重做的效果。MSG-01 / MSG-02 / OPS-05 |
| 3. 任务记录保存了，转码事件却没发出去？ | 本地事务、[Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) | 对比“写 DB 后直接发消息”和“任务+Outbox 同事务提交，再由发布者发送”，在各边界崩溃 | Outbox 保存可靠的发送意图，不是跨 DB/broker 的一次原子提交；发布者恢复后可继续发送，仍可能重复，需要消费者幂等。MSG-04 / DATA-04 |
| 4. 没收到心跳，是宕机还是暂时失联？ | [Heartbeat](https://www.rabbitmq.com/docs/heartbeats)、超时、故障怀疑 | 对同一 Worker 分别注入崩溃、进程暂停、消息延迟/网络分区；比较观察者判断 | 缺心跳不能证明节点已死；缩短超时也可能增加误判。观察者只能用已收到的消息，不能读取仿真器的全局真实状态。COORD-01 |
| 5. 新 Worker 接管后，旧 Worker 又恢复写入？ | Distributed Lock、Lease、[fencing / 世代号](https://static.usenix.org/events/osdi06/tech/full_papers/burrows/burrows_html/) | 暂停旧持有者，租约到期后让新持有者接管并写入，再放行旧写入 | 租约限制有效持有期，过期不会强制终止旧进程。首版假定一个可信租约授予者及明确时钟规则；资源端原子核对世代号，接受新世代后拒绝较旧写入，不能只靠客户端检查。COORD-02 |
| 6. 多步流程部分成功，怎么收场？ | Saga、[Compensation](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)、恢复进度 | 符号配额预留、转码成功后发布失败；清理产物、释放预留，再让补偿本身失败（也可手动在转码时拒绝） | 补偿是业务上的纠正，不是全局事务回滚，也未必恢复原样。记录待补偿项，允许重试或进入需人工处理状态；“已补偿”不等于发布成功。CONS-04 / OPS-05 / REL-02 |

ACK 与 checkpoint 会经常一起出现，但分别回答“对谁确认了哪一阶段”和“恢复从哪里继续”；幂等、Outbox、租约、补偿也各自保护不同边界，不互相替代。

## 这条故障路径的具体学习体验

1. **阅读路径已在 `/learn?path=failure-recovery` 接入**，从 `/practice` 可进入知识索引，与容量和状态正确性路径并列。相关概念与六讲实验均已接入，每个 Lab 可独立进入，不强制顺序解锁。
2. **可选热身**：先做现有 `service-queue-replicas` 和 `database-bottleneck`，观察等待与瓶颈。已有五题继续可独立进入，不要求先通关哈希或 Hot Key 才能学故障恢复。
3. **沿用学习闭环**：预测 → 注入故障 → 观察证据 → 改一个策略 → 换故障时刻重试。六题按各自语义显示网络消息、参与者局部状态、稳定账本和事件时序；支持步骤引导、自由操作、故障恢复与复盘。
4. **复用已完成的基础设施**：目录、题目版本、尝试记录、撤销、失效反馈、[算法会话与保存](../../apps/web/src/features/practice/algorithm/session.ts)。新增独立的版本化协议状态模型与渲染入口，记录逻辑消息、计时器、临时/稳定状态、业务效果和恢复步骤；不要伪造 `SimulationResult` 或让用例名称进入通用仿真内核。
5. **证据按保证评分**：把重试次数、消息交付次数、业务效果次数、ACK、checkpoint、当前权限分别展示。未完成/证据不足单独报告；不能因“没做任何事”而通过不重复检查，也不能以“一次运行没出错”声称普遍正确。通过后必须解释它仍没解决什么。

现状边界：共享仿真已有边级超时/重试、Topic 的部分 ACK，以及单次 run 内的 Workflow 去重、checkpoint 和补偿。独立协议 Lab 已有有界消息重投、消费调度、Outbox、本地故障检测、租约与资源 fencing，以及 Saga 恢复；它们没有改写共享 Queue/Workflow 语义，也不提供完整 broker、数据库或共识实现。共享引擎以[当前说明](../model-assumptions.md)为准；浏览器保存实验记录不等于业务持久性已被证明。

## 首个可操作协议 Lab：超时与幂等

第 1 讲已实现，ID `retry-idempotency` v1，入口 `/practice/retry-idempotency`。三个挑战分别是创建后丢响应、请求没有到达、旧请求延迟到达；也支持自由交错操作。

验收记录（2026-09-20）：完整 `pnpm check` 通过，包含 616 项单元/性质测试和 70 项浏览器测试。本轮新增 26 项协议模型/评分/保存测试及 4 项浏览器交互流程；核对了普通重试的重复效果、幂等修复、迟到/并发请求、参数冲突、精确过期、崩溃恢复、中途刷新、知识往返、窄屏和保存失败重试。

- [状态模型](../../apps/web/src/features/practice/retry-idempotency/model.ts)：`request-retry-v1`，每次操作都从空初态重放有界命令日志。递送、丢弃、原子处理、时间推进、崩溃、重启均为独立状态转换；不使用预置任务计数或 `SimulationResult`。
- [交互页](../../apps/web/src/features/practice/retry-idempotency/retry-lab.tsx)与[状态/时序视图](../../apps/web/src/features/practice/retry-idempotency/live-view.tsx)：逐条操作请求和响应，显示请求位置、客户端获知的结果、任务与幂等表。图中行距表示事件顺序，不表示耗时。三种策略对照也调用同一个状态模型。
- 计时合同：等待超时可选 100/500/1,000 ms，固定重试退避 0/100/500 ms，总尝试预算 1/2/3/5 次；不重试策略的有效预算为 1。推进时间先依序执行到期超时，再执行到期重试；手工递送发生在该命令之后。收到成功或参数冲突会停止新重试，但不会撤回旧在途请求；超时也不会取消服务端效果。
- 原子合同：作用域为 `(callerId, create-transcode, key)`，参数是规范化的 videoId/format。同键同参数重放，同键不同参数冲突；创建任务和记录键/参数/返回任务一起提交。保留期 200/2,000/10,000/60,000 ms，从首次提交起算，重放不续期；到期记录在下一次提交时清理，实际任务保留。过期或换键后可能重复创建。
- 恢复合同：进程崩溃丢失未提交收件箱，保留已提交任务与幂等记录；已经发出的网络消息仍存在。原子步骤内部不插入崩溃，不建模磁盘丢失、复制、外部副作用或真实转码。处理步骤为逻辑瞬时动作，不用其时间推导吞吐或延迟。
- 执行预算：最多 100 个命令、5 次发送、120,000 ms；所有历史/状态可完整重算。仍有在途消息或计时器时不能宣称结果已稳定；零任务也不能因零重复而通过。
- [评分](../../apps/web/src/features/practice/retry-idempotency/lesson.ts)分别检查完整证据、指定故障、单一效果、客户端结果确认、未完成工作及解释。普通重试在“请求丢失”场景可能达标，但在“创建后响应丢失”会产生反例；不能按策略名称直接评分。
- [保存](../../apps/web/src/features/practice/retry-idempotency/session.ts)使用独立 `retry-idempotency:v1` scope，复用原算法数据库而不改变旧记录格式；当前操作自动保存，核验生成不可覆盖的尝试，撤销和刷新可以恢复到消息尚在网络中的中间状态。
- 验证入口：[模型测试](../../apps/web/src/features/practice/retry-idempotency/model.test.ts)、[评分测试](../../apps/web/src/features/practice/retry-idempotency/lesson.test.ts)、[保存测试](../../apps/web/src/features/practice/retry-idempotency/session.test.ts)、[浏览器手动流程](../../apps/web/tests/retry-idempotency.spec.ts)。模型含独立 Map 去重参考及并发交错、参数冲突、精确过期、丢请求/响应、崩溃与迟到请求反例。

- 最小模型：一个客户端、任务服务和符号稳定任务表；一项逻辑提交意图、有限重试预算、可控制的请求/响应丢失与超时。相同幂等键只在同一调用方/操作范围内表示同一意图；同键不同参数必须冲突，去重保留期与迟到重试边界明确可见。
- 策略对照：不重试 / 普通重试 / 同键幂等重试。以“创建后丢响应”为核心反例；同时验证“请求未到达”时还要能够完成，不能一律拒绝以换取零重复。连续故障耗尽预算时显示未知/未完成；有限重试也避免无限放大负载。
- 验收：在声明可恢复、预算足够的场景，只有一个任务、重试获得该任务的结果；并发同键提交的判重与创建必须原子完成，不能先查后写。换一个故障时刻仍能解释结果，输入变更使旧结论失效，刷新恢复且与已有五题隔离。
- 第 2–6 讲现已按独立模型实现，合同见下节。六次学习时长不是开发工期；当前完成的是限定入门路径，完整能力矩阵继续按专题扩展。

## 第 2–6 讲：可执行合同与接入

这五个 Lab 使用真实执行的有界命令日志计算结果；“运行完整示例”只是逐条执行相同命令，手动交错消息也走相同状态转换。每题具有三个故障挑战和自由操作、自动保存、不可覆盖的核验尝试、撤销/重做、状态变化后的旧评分失效，以及相关知识回链。题目 scope 和模型版本各自隔离，不把旧记录套入新语义。

| Lab / 入口 | 可操作场景 | 模型合同 |
|---|---|---|
| `ack-checkpoint` / `/practice/ack-checkpoint` | 处理前崩溃、效果后崩溃、消费 ACK 丢失；自由模式可乱序完成、丢投递、重投至死信并重放 | [message-flow-v1](../../apps/web/src/features/practice/message-flow/model.ts)：逻辑消息、发布副本、投递凭据分别标识。可见性到期释放额度并调度重投，不停止旧执行；旧 ACK 不能确认新凭据。比较提前 ACK、效果与进度分开提交、效果与 Checkpoint 原子提交 |
| `transactional-outbox` / `/practice/transactional-outbox` | 提交后发布前崩溃、发布后发送标记前崩溃、消费效果后崩溃 | 复用消息模型：任务与 Outbox 本地原子提交；发布确认、发送标记和消费效果是不同边界。恢复后以相同逻辑消息 ID 重发；重复副本仍需消费去重。生产者进程世代隔离旧确认 |
| `heartbeat` / `/practice/heartbeat` | 暂停、分区、崩溃；任意丢弃或延迟心跳，恢复后继续递送 | [coordination-v1](../../apps/web/src/features/practice/coordination/model.ts)：观察者只依据收到心跳的时刻判断；旧世代/旧序号不刷新超时，但尚未见过的迟到心跳可以清除怀疑，即使发送者已崩溃。真实状态和局部判断分开显示 |
| `lease-fencing` / `/practice/lease-fencing` | 旧写入迟到、怀疑产生但租约尚有效、资源还没见到新 token | 单一可信授予者和教学共享钟；申请/续租抽象为同步往返。租约到期保留旧内存及在途写入。资源原子检查最高已接受 token；低世代拒绝，同世代乱序和新 token 到达前的窗口不被此规则保护 |
| `saga-recovery` / `/practice/saga-recovery` | 补偿响应丢失、补偿效果后记进度前崩溃、补偿本身失败至人工处理 | [saga-v1](../../apps/web/src/features/practice/saga/model.ts)：预留→转码→发布；失败后按已确认步骤清理产物→释放配额。服务效果与本地去重原子，协调者另存日志。幂等 ID 为流程/步骤，成功及业务拒绝保留，暂时不可用可重试。补偿预算耗尽需核查后恢复，不能直接标成成功 |

**消息模型边界**：单一逻辑生产者/消费者；最多 3 个任务、12 次发布、30 次投递、150 个命令、120,000 ms。接纳、ACK、到期、重放等动作驱动 broker 调度，停止生产也能继续排空。效果是完成账本追加，Checkpoint 是逻辑消息的已处理集合；连续完成位置为任务序号，不是 Kafka offset。死信重放保留消息 ID 和历史次数，本轮预算重置；“处理失败”是显式注入，不代表执行了真实 schema 修复。稳定 broker/存储是前提，无 broker 崩溃、多分区重平衡或外部效果恰好一次保证。

**协调模型边界**：两个 Worker、观察者、授予者与资源；最多 100 个命令、200 条心跳、20 条写入、10,000 ms。暂停保留内存，崩溃清除本地租约，重启世代单调为假设；网络包不因崩溃或过期自动撤销。观察超时先于随后手动递送。样本预算耗尽时不给故障验证通过。无时钟偏差、Raft、授予者崩溃或成员共识。

**Saga 模型边界**：一个视频流程；最多 150 个命令、30 次调用、10,000 ms。协调者崩溃失去未记录响应，但业务效果、日志和网络包保留；用同一操作 ID 重试。释放配额是增加可用余额的业务动作，关闭幂等可观察重复返还；清理产物不撤销累计转码工作。检查器同时核对最终账本、日志、指定故障、在途工作与解释，不以“compensated”状态或策略名称直接判通过。无并发 Saga、真实支付、磁盘损坏或全局事务隔离。

实现入口：[消息 UI 与评分](../../apps/web/src/features/practice/message-flow/)、[协调 UI 与评分](../../apps/web/src/features/practice/coordination/)、[Saga UI 与评分](../../apps/web/src/features/practice/saga/)；共享[事件视图](../../apps/web/src/features/practice/protocol/event-timeline.tsx)和既有 Lab 保存合同。浏览器验收覆盖[消息流程](../../apps/web/tests/message-flow.spec.ts)、[协调流程](../../apps/web/tests/coordination.spec.ts)、[Saga 流程](../../apps/web/tests/saga.spec.ts)，包括手动操作、知识往返、刷新恢复、跨题隔离和窄屏；模型与保存测试位于对应目录。

## 并发与过载扩展：可执行合同

这两个 Lab 延续预测、手动操作、证据核验与复盘，进入现有“状态正确性与恢复”“容量、分布与热点”路径。通用页面部分复用 [ProtocolExperiment](../../apps/web/src/features/practice/protocol/experiment.tsx)，模型、评分与保存作用域仍由各题维护，没有把新机制塞进共享容量引擎。

| Lab | 三个挑战 | 明确验收 |
|---|---|---|
| `concurrent-update` · [并发模型](../../apps/web/src/features/practice/concurrent-update/model.ts) | 最后一个名额的竞争；两个名额的丢失更新；读取后、提交前崩溃 | 库存非负、库存+预订=初始容量、不得超卖或重复意图；两任务都得到业务结论，锁释放。必须经历实际交错，改变名额或只串行运行不能替代挑战 |
| `overload` · [过载模型](../../apps/web/src/features/practice/overload/model.ts) | 减速后的重试放大；突发与有限队列；总截止期后仍在工作 | 固定 12 个原始请求、单执行槽与故障窗口；分别检查及时成功、尝试/执行代价、峰值队列、拒绝/过期/未完成。最后一关要求观察成功与迟到完成，并阻止截止后启动新工作，不把丢弃计为成功 |

**并发合同**：`concurrent-update-v1`，两个独立预订意图，一行库存和预订账本。所有策略的单次提交都原子写入库存和预订；先读后写缺少隔离，仍可超卖或丢失扣减。CAS 在同一步检查版本并提交，失败必须重读；行锁从读取持有至提交或中止，FIFO 等待者获锁后重新读取。同意图去重与并发策略分别配置，用于证明幂等不能代替不同意图间的冲突控制。

崩溃操作假定数据库已识别会话结束并中止未提交事务，已提交预订保留；不建模真实网络故障检测延迟。最多 60 个命令、12 条预订；动作是逻辑交错而非耗时。无多行写偏斜、MVCC、死锁或通用事务隔离级别。该 Lab 的局部原子前提不意味着共享 DB 已实现事务。

**过载合同**：`overload-v1`，原始请求、客户端发送窗口、FIFO 队列与处理槽分别记录。原始到达是每 100 ms 一个或同时突发；每个尝试是独立的符号只读工作，没有服务端去重缓存。正常处理 100 ms，减速时新工作 500 ms；已开始的工作保留原耗时。挑战减速窗口固定在 0–600 ms。每次等待 200 ms 后可重试，总截止期从原始到达算起为 3,000 ms，最后一关为 800 ms；客户端窗口中的等待也消耗截止期。

立即重试、无重试、400/800/1,600 ms 指数退避和附加 0–200 ms 确定性抖动共四种策略；抖动种子不改变需求或故障。每请求最多 1/2/3/5 次尝试；窗口限制尚未获得结果的原始请求，不等于执行槽。队列上限拒绝多余尝试，过期检查只丢弃尚未开始的工作。成功取消未来重试，不撤回已排队/运行的尝试；停止新到达也不停止重试或排空。

同一时刻先处理完成响应，再处理总截止期、尝试超时和到达/发送；在截止时刻完成可成功，截止时刻尚未开始的工作不能再启动（开启过期检查时）。最多 20 个原始请求、100 次尝试、100 个命令和 10,000 ms。逐事件采样展示服务端与客户端等待，所有尝试满足“完成+拒绝+过期出队+排队+执行中=总尝试”；没有网络丢包、熔断、业务降级、令牌桶或分布式限流协议。

实现与验收入口：[并发页面与评分](../../apps/web/src/features/practice/concurrent-update/)、[过载页面与评分](../../apps/web/src/features/practice/overload/)、[保存合同测试](../../apps/web/src/features/practice/protocol/extension-sessions.test.ts)、[浏览器流程](../../apps/web/tests/concurrency-overload.spec.ts)。过载测试遍历重试/队列/窗口组合核对守恒；并发测试枚举两事务读写交错。浏览器覆盖手动构造反例、改策略、刷新到中间状态、保存失败重试、跨题隔离、键盘与窄屏。

验收记录（2026-09-20）：完整 `pnpm check` 通过，包含 719 项单元/性质测试与 82 项浏览器测试。本批新增 37 项模型/评分/保存测试及 4 项浏览器流程；此前 682/78 为六讲故障恢复路径的历史基线。

## 复制、共识、原子提交与持久恢复

以下五个 Lab 接入同一目录、知识页、保存合同及 [ProtocolExperiment](../../apps/web/src/features/practice/protocol/experiment.tsx)。共同的[版本化题目合同](../../apps/web/src/features/practice/protocol/lesson.ts)只负责完整重算、作答和保存核验；协议状态转换与判据仍属于各自模型。每题都提供步骤引导、自由调度、策略比较及可恢复的中间状态。

| Lab / 入口 | 可操作挑战 | 验收依据 |
|---|---|---|
| `replica-consistency` | 写后读取延迟副本；先新后旧的读取；副本分区与恢复 | 固定主节点写确认后，比较任意副本、会话最低版本和固定主节点读取；核对实际返回历史，不能用最后追平抹掉旧读 |
| `quorum-reads` | R/W 交集；异步读修复；局部 tag 的多数派反例 | 逐副本接纳、不同成员确认集合、返回前实际收到的回复；构造 R+W>N 但局部 tag 不尊重实时顺序的反例 |
| `raft-consensus` | 分票后重选；少数派旧 Leader；冲突后缀恢复；旧任期多数复制 | 任期与稳定投票、prevIndex/prevTerm、matchIndex 和实际应用记录；不同任期的自认 Leader 不自动等于安全性违例，旧任期多数份副本不能直接确认 |
| `two-phase-commit` | 准备后协调者崩溃；决议只到达一个参与者；参与者恢复与重复决议；NO 投票 | 稳定 Prepared、资源锁、唯一持久决议、本地业务效果和最终确认；错误的准备后超时自行中止会暴露 commit/abort 冲突 |
| `durability-recovery` | 内存确认后崩溃；未提交 redo；检查点后的重放；指定提交边界恢复；损坏归档与备用副本 | 易失/稳定 WAL、数据页、备份和归档的实际内容；恢复不读取客户端确认清单来补造数据，缺失或损坏目标范围报告失败 |

**复制与 Quorum 合同**：[replicated-register-v1](../../apps/web/src/features/practice/replication/model.ts)，三个固定副本、两个客户端、单个字符串寄存器，最多八个用户操作、150 条消息和 150 个命令。固定主节点 A 模式在本地提交后确认，异步复制；会话令牌携带已观察版本，约束后续非重叠读取，版本不足时等待。无选主或故障切换保证。副本进程崩溃保留稳定值，已经发出的消息保留；隔离阻止双向递送，恢复后可继续。

Quorum 模式采用独立客户端计数器和客户端 ID 组成的全序 tag；副本保留最高 tag，写确认表示处理过该 tag。读取使用最先收到的 R 个不同副本回复，迟到回复不改写已返回结果。异步读修复在读返回后向已回复的旧副本发送；它不实现 ABD 的返回前多数派写回，也不是共识。完整[寄存器历史检查器](../../apps/web/src/features/practice/replication/history.ts)枚举合法顺序并保留实时先后，输出见证或反例；有未返回操作时报告未完整，不删除它们后宣称通过。该检查只验证有限历史，不证明整个协议。

**Raft 合同**：[raft-v1](../../apps/web/src/features/practice/raft/model.ts)，固定三/五成员，稳定 term/votedFor/log，RequestVote 与 AppendEntries 的显式请求/回复。应用状态与进度在本模型中一同持久保存；选举和复制进度是临时状态。每任期按不同成员计票，候选日志先比最后任期、再比长度；复制拒绝不匹配前缀，回退 nextIndex，替换未提交冲突后缀。迟到失败回复不回退已更新的请求进度。只有本任期条目满足多数复制才推进提交，其前缀同时应用；错误的“任何任期只数副本”规则作为单独反例选项。规则参考 [Raft 扩展论文的算法摘要与旧任期提交讨论](https://raft.github.io/raft.pdf)。

Raft 的超时由用户显式触发，心跳使用空 AppendEntries；不模拟随机计时、预投票、读取租约、成员变更或 InstallSnapshot。最多 240 个命令、400 条消息、10 个提案及每节点八条日志。全局安全检查只观察记录，不向节点提供选主或恢复信息；隔离消息和未确认提案保留可见。已提交冲突会报告反例并停止该冲突重试，不强行改写数据来获得成功。

**2PC 合同**：[two-phase-commit-v1](../../apps/web/src/features/practice/two-phase-commit/model.ts)，一个协调者、两个参与者和单个 txn-1，符号余额从 5/5 转为 3/7。准备意图与 YES 稳定记录后才回复，协调者先持久记录唯一 commit/abort 决议再发送。参与者效果和终态本地原子提交，重复决议不重复效果。协调者重启丢失已收投票/确认，可从稳定决议重发或重新收集稳定承诺；参与者重启保留 Prepared/终态。准备后超时不提供决议信息，正确模式保留锁等待；阻塞边界参考 [Gray 与 Lamport 的事务提交论文](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2003-96.pdf)。

2PC 不实现全局快照隔离、多事务竞争或 Paxos Commit。参与者物理应用时刻不同，仍准备的资源保持锁定，不能把中途原始余额之和当成跨库一致读。最多 120 个命令、80 条消息和 10,000 ms。

**持久恢复合同**：[durability-v1](../../apps/web/src/features/practice/durability/model.ts)，四个以内的串行本地事务、redo-only WAL、数据检查点、两份独立快照备份和两份日志归档。update/commit 分开追加，刷盘才进入稳定前缀；确认可比较内存与 WAL 条件。数据检查点必须在对应 WAL 稳定之后安装。进程恢复从数据页开始，仅应用有 commit 的 redo；损坏或缺失的目标日志不能跳过。

指定时点恢复明确选择备份、归档和提交 LSN，目标之后的确认写入被有意排除；恢复完成安装结果，可以再次重启验证，但本题不在恢复后的新时间线上继续写入。完整性是符号检查，未实现真实文件格式、fsync、脏页 undo、MVCC、物理盘故障或真实 RTO。最多 120 个命令、八条本地日志。客户端确认与事务意图只用于界面/评分，恢复算法不读取它们来修补数据。

验证入口：对应目录中的模型测试；[五个作用域的保存测试](../../apps/web/src/features/practice/protocol/advanced-sessions.test.ts)；[浏览器手动流程](../../apps/web/tests/state-correctness.spec.ts)。Raft 另对 30 个种子的三/五节点有界调度检查任期唯一性、前缀匹配与应用安全性。所有验收仍受模型声明的故障和范围约束。

验收记录（2026-09-20）：完整 `pnpm check` 通过，包含 754 项单元/性质测试与 87 项浏览器测试。本轮新增 35 项模型/历史检查/保存测试和 5 项浏览器流程。随后补充最大合法字符串的窄屏换行验证，重新构建并通过全部 87 项浏览器测试；基础知识与实验回链也做了复验。

## 使用者场景回归（2026-09-21）

通过隔离的浏览器会话复现并修复了三条使用路径，未用真实用户记录做破坏性测试：

| 用户场景 | 原问题 | 修复 |
|---|---|---|
| 同一道题开两个标签页，分别操作后刷新 | 后写的旧草稿静默覆盖先保存的操作 | 在 IndexedDB 事务内检查草稿修订号；过期写入不修改草稿或尝试记录，本页未保存操作保留并显示冲突 |
| 保存格式未知或读取失败后点重试 | 初始草稿可能被当作当前记录重新保存，清掉原有操作 | 读取失败时禁止修改与保存，重试执行重新读取；加载 Promise 失败后可再次尝试 |
| Raft 五节点选择 D/E，再切换到三节点 | 下拉框显示 A/B，内部仍保留已不存在的节点，提案按钮不可用 | 成员数变化时重置操作面板，显示选择与实际发送目标一致 |

共用算法/协议保存层的数据库升级到 schema 2，保留旧 `sessions` 表与不可覆盖的 `attempts`，将当前草稿迁移到带修订号的 `drafts`。旧客户端后续写入留在旧表，不能覆盖新草稿；尚未建立新草稿的作用域支持从旧表恢复，并检查首次接管时的竞争。不自动合并新旧标签页分支。

冲突或写入失败时可导出本页草稿与已加载的尝试，再明确选择舍弃本页未保存修改并重新读取。导出格式为 `system-design-lab-recovery`，用于保留本页证据，不是整库备份，也不是自由工作台的 `ProjectFile` 导入格式。保存层的修订号和 schema 版本不改变实验模型版本或原有尝试的判据。

回归入口：[保存恢复与迁移测试](../../apps/web/src/features/practice/algorithm/storage-recovery.test.ts)、[学习者浏览器流程](../../apps/web/tests/learner-recovery.spec.ts)。覆盖未知版本、临时读取失败、双标签页、旧数据迁移、冲突导出、Raft 参数切换，以及知识页往返、刷新和窄屏操作。

全量检查还暴露了 CPU 密集的 Hot Key 保存回归在过高并行度下触发 5 秒超时的问题。单独运行及最多四个并行文件的对照均通过；Web 单测现按可用 CPU 限制到最多四个 worker，保留原有时间预算和完整测试覆盖。

验收结果：完整 `pnpm check` 通过，包含 761 项单元/性质测试和 93 项浏览器测试；本次新增 7 项保存/迁移测试及 6 项学习者流程回归。
