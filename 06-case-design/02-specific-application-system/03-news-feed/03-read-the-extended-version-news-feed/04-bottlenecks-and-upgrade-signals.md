#Bottlenecks and upgrade signals

## What is solved in this version?

- Write traffic and homepage read traffic no longer compete for the same batch of database resources.
- API and read replicas can be scaled horizontally.
- Popular Post text and repeated first-screen reads gain cache benefits.
- The system still maintains the simplicity of synchronous writes and relational database transactions.

## It doesn't solve anything

Every time there is a cache miss, the system still has to look for candidate Posts based on the Following field. Costs generally increase with the following factors:

```text
Number of read requests × Number of followers per person × Number of candidate posts scanned
```

The user homepage is highly personalized, and the reuse rate of the complete feed cache is very low; continuing to add Redis cannot cure JOIN and candidate scanning.

## Signal to enter the fourth edition

- After adding read replicas, the CPU time for a single feed query continues to increase.
- The P99 of high-concern users is significantly higher than that of ordinary users.
- A cache miss or Redis failure can quickly exhaust the entire Read Replica capacity.
- Database costs are mainly generated by double counting the same "which pages the post belongs to".

These signals indicate the need to move computation to post-write in the future. But FeedItem cannot be cut immediately; the fourth version first creates Outbox, events and derived indexes, and keeps the online reading path unchanged.
