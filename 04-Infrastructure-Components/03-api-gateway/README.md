# API Gateway

An API gateway is the unified policy entry point for business APIs. It identifies the API, caller, and tenant; enforces common cross-service rules; and then routes the request to a business service.

This article focuses on using an off-the-shelf gateway. For a complete design, see the [API Gateway case study](../../06-case-design/01-common-basic-system/02-api-gateway/). The mechanisms behind authentication, rate limiting, and retries belong to [Core Concepts](../../02-core-concepts/).

## 1. Differences from Other Entry Components

| Component | Primary decision | Not responsible for |
|---|---|---|
| DNS / global traffic | Which region or global entry point the user enters | API identity and business routing |
| Load balancer | Which healthy instance receives a request | Caller quotas and domain permissions |
| API gateway | Whether an API request is allowed, which policies constrain it, and which service receives it | Domain logic such as orders, pricing, or feed ranking |

One product may implement multiple responsibilities, but the design must still separate them so that configuration and failure boundaries are explicit.

## 2. Position and Data Bypass

    Client
      → DNS / Global Entry
      → Regional Load Balancer
      → API Gateway
      → Business Service

Regular control requests and small business requests pass through the gateway. For large byte streams such as images, video, backups, and map tiles, the gateway usually performs authorization only; the client then connects directly to object storage or a CDN using a short-lived signed URL or cookie.

## 3. Input, Output, and Success Semantics

| Item | Description |
|---|---|
| Input | Protocol request, route, identity credentials, tenant context, and policy configuration |
| Output | Rejects the request, or forwards it to a backend and returns the response |
| Gateway success | Common policies passed and the request was proxied according to the routing contract |
| Does not mean | Business success, a committed write, or completed asynchronous work |

Errors generated by the gateway should be distinguishable from backend errors. Do not rewrite every failure to the same 500 response.

## 4. What Is Suitable for Central Enforcement

- routing by host, path, method, version, and tenant;
- authentication entry using tokens, API keys, or mTLS, plus identity normalization;
- coarse-grained API access control;
- rate limits and quotas by caller, tenant, API, or plan;
- request-size, header, content-type, and basic schema checks;
- timeouts, bounded safe retries, concurrency limits, and common circuit-breaker configuration;
- request IDs, trace context, access logs, and audit fields;
- CORS, protocol conversion, consistent error formats, and canary routing.

A rule should be common across businesses, and the gateway must possess the information needed to make the decision.

## 5. What Should Not Be Put in the Gateway

- domain decisions such as order state, inventory deductions, and feed ranking;
- fine-grained authorization that requires querying multiple business databases;
- long-running computations and background jobs;
- forwarding large files, video segments, and static content;
- business idempotency, compensation, and consistency rules;
- shared scripts that grow continually with the business.

The gateway can verify that a caller has the `order.write` scope; the Order Service must still decide whether the user may modify a specific order.

## 6. Authentication, Authorization, and Identity Propagation

A gateway can validate a signed token locally or call an external authentication service. Local validation removes a per-request dependency, but key rotation, issuer, audience, expiration, and revocation must be defined. A synchronous call can obtain current status, but it adds authentication-service latency and failures to every request.

After validating external credentials, remove any client-forged internal identity headers, then write trusted User ID, Tenant ID, scope, and authentication context fields. If the backend is reachable through other paths, a network or service-identity boundary is also required.

Do not use a single global fail-open switch when a dependency fails:

| Dependency | Common approach |
|---|---|
| Identity cannot be verified | Fail closed, except for public anonymous APIs |
| Permissions cannot be determined | Usually fail closed |
| Rate-limit store fails | Decide by API risk; conservative local limiting may be possible |
| Audit write fails | Compliance requirements determine whether to reject or buffer |

## 7. Rate Limits, Quotas, and Concurrency

- A rate limit bounds the rate over a short interval.
- A quota bounds total use over a longer period.
- A concurrency limit bounds the number of expensive requests running simultaneously.

Explicitly state whether counts are by user, tenant, API key, IP, or route; how much bursting is allowed; what an excess request returns; and how much divergence is acceptable for multi-region counters.

The gateway protects only traffic that passes through it. Internal calls, consumers, and bypass uploads need their own capacity protection. For a complete design, see the [Rate Limiter case study](../../06-case-design/01-common-basic-system/04-rate-limiter/).

## 8. Timeouts, Retries, and Request Size

The gateway timeout should be shorter than the client's total deadline and leave time to return the response. Backends should inherit a shorter remaining duration instead of receiving a fresh full budget at every layer.

A gateway should not retry every request by default. Consider a bounded retry only when the failed stage is known to be retryable, the operation is a read or has a reliable idempotency boundary, the attempt count is limited, and backoff is used. If a write such as a payment, seat reservation, or resource creation has an uncertain result, retrying against another instance cannot prove that the first attempt failed.

Use a dedicated path for large files: the client first requests authorization; the business service creates metadata and issues a URL constrained by key, size, and lifetime; then the client uploads directly to object storage. For the object contract, see [Large Objects and Object Storage](../../03-data-and-storage/06-large-object-and-object-storage/).

## 9. Routing, Versions, and BFFs

Routes may use host, path, method, header, caller, or version. Define their priority and detect conflicts. A version may appear explicitly in the URL or a header, or traffic may migrate by caller, tenant, or a small percentage.

A backend for frontend (BFF) can provide different aggregation for web and mobile clients, reducing client round trips. A BFF should be an owned, independently deployable service, not continually growing page-specific business logic in gateway configuration.

## 10. Control-Plane and Data-Plane Contract

When using a product, verify:

- how long configuration takes to reach every data plane;
- whether new configuration is validated, canaried, and quickly rolled back;
- whether the data plane can continue serving with the last valid configuration during a control-plane failure;
- whether a failed configuration update can leave instances on inconsistent versions;
- how keys, certificates, and policies are rotated and audited;
- whether data-plane requests synchronously depend on the control plane.

## 11. Quotas, Capacity, and Cost

| Item | What to verify |
|---|---|
| Requests and connections | QPS, concurrency, long-lived connections, and burst capacity |
| Payload | Limits on URLs, headers, bodies, compression, and decompressed size |
| Policies | Route count, plug-in count, execution time, and external calls |
| Timeout | Maximum integration duration, idle timeout, and streaming |
| Protocols | HTTP, gRPC, WebSocket, and SSE |
| Logging and tracing | Sampling, redaction, storage volume, and cost |
| Multitenancy | Policy and quota isolation, configuration scale, and propagation speed |

TLS, token validation, complex policies, large headers, logging, and protocol conversion all add cost. Estimating QPS alone is insufficient.

## 12. Failure and Overload Behavior

| Situation | External behavior |
|---|---|
| Data plane overloaded | Rising latency, 429, 502/503, or connection failure |
| Control plane fails | New configuration cannot be published; whether old configuration continues depends on the product |
| Identity provider fails | New sign-ins fail; existing tokens may still validate locally |
| Rate-limit store fails | Excess requests are admitted or valid requests are rejected |
| Backend slows down | Proxy queueing, timeouts, or connection-pool exhaustion |
| Bad route is published | Some APIs return 404, enter the wrong version, or fail entirely |

The gateway is a shared entry point, so a bad policy amplifies the blast radius. Roll out configuration gradually by tenant, route, or instance batch.

## 13. Product Forms and When a Gateway Is Unnecessary

| Form | Examples | Primary tradeoff |
|---|---|---|
| Cloud-managed gateway | Amazon API Gateway, Azure API Management, Google Cloud API Gateway | Less operations work; examine protocols, quotas, geography, and pricing |
| API management platform | Apigee, Azure API Management | API products, developer portals, policies, and analytics |
| Self-hosted gateway | Kong, NGINX, Envoy ecosystem | Flexible; the team owns capacity, high availability, upgrades, and plug-in risk |
| Kubernetes gateway | A concrete Gateway API or Ingress implementation | Integrates with cluster discovery; capabilities depend on the implementation |

If the only need is to distribute traffic among healthy instances, an L7 load balancer may be enough. A separate gateway gains clear value when common authentication, caller governance, API lifecycle, or multi-protocol access is needed.

## 14. Application Responsibilities and a Small Case Study

The application remains responsible for domain authorization and business invariants, write idempotency and result queries, backend capacity and degradation, API compatibility, post-upload validation, protection for traffic that does not pass through the gateway, and sensitive fields and data residency.

For a news feed, reading the feed and creating a post pass through the gateway, which validates the token and propagates User ID and Tenant ID. Creating a post carries an idempotency key, but the Post Service performs deduplication. Images upload directly through a short-lived URL. The gateway does not automatically retry a post whose outcome is uncertain. Metrics should distinguish 401/403, 429, gateway 5xx, and backend 5xx responses.

Before selection, answer:

- Does the current problem exceed the capabilities of a load balancer?
- Which rules are common across businesses, and which belong to domain services?
- Where is identity validated, and why are internal identity fields trustworthy?
- What dimensions define rate limits, quotas, and concurrency limits?
- Are timeouts and retries within one end-to-end budget?
- Which traffic should bypass the gateway or use a dedicated entry point?
- How does the data plane operate during a control-plane failure?
- After adopting a managed product, what remains the application's responsibility?
