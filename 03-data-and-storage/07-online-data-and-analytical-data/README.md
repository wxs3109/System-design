# Online data and analytical data

Online requests and analytical queries face the same business, but have different access modes. The design goal is not to stuff all data into a "universal database", but to make the transaction path stable and low-latency, and the analysis path can scan and aggregate large amounts of historical data**.

This section only compares data roles, storage forms, and application-visible trade-offs. Reliable links for ETL, CDC, and streaming batch processing belong to [Common Design Pattern](../../05-general-design-patterns/).

## The difference between OLTP and OLAP

| Dimensions | Online Transaction Processing (OLTP) | Online Analytical Processing (OLAP) |
|---|---|---|
| Typical operations | Create orders, update posts, read user homepages | Summarize revenue by month, funnel analysis, training features |
| Single visits | A small number of rows or a business aggregation | A large number of rows, columns, or historical partitions |
| Latency target | Milliseconds to lower seconds | Seconds, minutes, or more, depending on the scenario |
| Concurrency form | A large number of short requests | Few but resource-consuming queries |
| Writing | High-frequency small transactions | Batch import, streaming append or periodic merge |
| Main correctness | Current business status and transaction invariants | Complete data, stable caliber, and interpretable time range |

The problem with reports directly querying the main production database is not just "SQL is slow". Large scans, complex joins, and aggregations compete for CPU, memory, I/O, and number of connections, making the tail latency of transaction requests unpredictable.

## Row-oriented and Columnar Storage just need to know the purpose

- **Row storage** puts the fields of a row together, suitable for reading or modifying complete business objects by primary key, and is also suitable for short transactions.
- **Column storage** makes data in the same column more suitable for batch scanning, compression and aggregation, and is suitable for analytical queries that only read a few columns but cover a large number of records.

This is just a performance bias, not a guarantee independent of data volume, indexes, partitions, queries, and product configurations. The application design does not require expanded page layout, vectorized implementation, or compression algorithms.

## Warehouse, Lake and the role of Lakehouse

| Form | What is more suitable | Main limitations | Represent product or technology |
|---|---|---|---|
| Data Warehouse | Governed structured tables, stable BI queries and high-concurrency reports | Data import and modeling are costly, and the original format has low flexibility | Snowflake, BigQuery, Redshift, Fabric Warehouse |
| Data Lake | Save raw or multi-format large-scale data at low cost | Only files do not mean transaction, governance and fast query capabilities | Data files on S3, ADLS, GCS |
| Lakehouse | Adds table format, version and query management to object storage data | Components and operation and maintenance boundaries are more complex, and capabilities depend on specific engines | Delta Lake, Apache Iceberg, Fabric Lakehouse |

Product names are not a substitute for needs analysis. Before selecting, you still need to specify the data size, query concurrency, freshness, update method, governance requirements and cost limit.

## Three types of common data

| Data | Examples | Common authority relationships |
|---|---|---|
| Current business status | Current order status, post visibility, Item definition | Online business stores are often authoritative sources |
| Immutable business events | OrderPaid, VideoPlayed, JobCompleted | Event records describe the facts that have occurred; producers and event versions need to be defined |
| Analysis model | Daily activity, revenue summary, recommendation features, semantic indicators | Usually recalculated derived results |

Whether a table in the analysis platform is authoritative must be judged according to the data contract and cannot be called a copy. For example, an approved financial settlement ledger might be the authoritative record, while the monthly statements generated by it are still derivatives.

## Data Freshness should be written as a clear time goal

Instead of just saying "real-time" or "eventually consistent", write:

- What are the event occurrence time and platform reception time;
- How long will it take for 99% of the data to be queried;
- How long is late data allowed and how to correct it after the window is closed;
- Whether Backfill covers the same partition, and how to remove duplicates from the result;
- Which time point or batch of data does the Dashboard display?
- How long does it take for the analysis results to be updated after the source data is corrected or deleted.

For example: "Enter the operation dashboard within 5 minutes after the order is paid, and 99.9% is completed within 30 minutes; the financial report is closed the next day, and late records are processed through revision batches." This is more constraining on the design than "use real-time stream processing".

## Boundary between online and analytical

The recommended approach is:

```text
Online business storage -> changes or business events -> analysis storage -> semantic model/report
     |                                      |
Transaction requests only rely on scanning, aggregation and historical queries here
```

The following rules need to be clarified:

- Users should not wait for report updates if their transactions are successful;
- Analytical queries should not directly compete for key resources of the production main database;
- Event fields have stable meanings and versions, and internal row changes in the database cannot be directly regarded as complete business semantics;
- The analysis data is organized according to common filter conditions such as tenant and date to avoid full scanning every time;
- PII, permissions and deletion requirements follow the data into the analytics layer, rather than being copied and lost to governance;
- When writing the analysis results back to the online system, treat it as a new derived input and define version and expiration rules.

## When is it not necessary to analyze the platform separately?

In early systems, if the amount of data is small, reports are few, and queries are controllable, read-only copies, scheduled exports, or simple summarization within the database can be used. Separate after the following signals appear:

- Report scanning affects the tail delay of online requests;
- Historical data exceeds the economic retention range of the online database;
- Multiple business sources need to be analyzed uniformly;
- Queries require large-scale aggregation, long-term history, or columnar capabilities;
- Analytics teams and online services require independent capacity and change cadence.

## Case: Multi-tenant data platform

In [Multi-tenant Data Platform](../../06-case-design/03-platform-system/01-multi-tenant-data-platform/), it is possible to distinguish:

| Plane | What to save | Typical operations |
|---|---|---|
| Control plane metadata | Tenant, Workspace, Item, Operation, Permissions and Capacity configuration | Small transactions, enumeration and status changes |
| User data plane | File, table, Snapshot and commit metadata | Large object reading and writing, table reading and computing input and output |
| Operational analysis surface | Usage, auditing, job indicators and aggregate reports | Historical scans, aggregation and capacity trends |

Capacity Manager can read Usage summaries within the latency tolerance range for planning purposes, but cannot blindly trust a lagging daily report for quota deductions or security denials. Whether to enter the online decision-making path determines how strong the freshness and correctness guarantee of the data is.

## Common out-of-control points

- Think of the data lake as "putting files in and they can be queried naturally";
- Let BI queries directly access the production master database;
- Does not distinguish between event occurrence time and processing time, resulting in window statistics that cannot be interpreted;
- Each team defines different `active_user` or `revenue` calibers;
- Analysis copies retain deleted or revoked data;
- Introducing expensive stream processing in pursuit of "real-time" without the goal of business freshness.

## Checklist

- [ ] The access patterns and latency targets of online requests and analytical queries have been separated;
- [ ] The transaction path does not rely on unnecessary analysis result updates;
- [ ] The authoritative relationship between the current status, business events and analysis model is clear;
- [ ] Data freshness, lateness, revision and Backfill have time contracts;
- [ ] There is resource isolation between report query and production system;
- [ ] Tenant, permissions, PII, retention and deletion requirements extend to analytical copies;
- [ ] Selection of Warehouse, Lake or Lakehouse is based on access patterns, not product popularity.
