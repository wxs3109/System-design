# How to asynchronously: Message Model and selection

Before choosing an asynchronous mechanism, first determine two things: whether the sender expresses "please do one thing" or "something has happened"; whether this message should be processed by one Consumer, or multiple Consumers should be allowed to process it once.

## Command, Event and execution results

### Command: Expect a certain receiver to perform an action

`GenerateThumbnail`, `ChargePayment` are Commands. Commands can be rejected, can fail, and usually have a clear execution owner and result status. Use the imperative mood when naming, and bring with it the stable identification needed for execution.

### Event: State a submitted fact

`PostCreated`, `OrderPaid` are Events. The Producer should not know all subscribers, nor should it stuff "what do I want the consumer to do" into the event name. Events are named in the past tense; Consumer failure does not reverse a fact that has already occurred.

For example, `SendWelcomeEmailEvent` is actually a Command - it specifies an action. `UserRegistered` is a fact, and email, analysis and risk control can each decide what to do with it.

### Execution results: new facts generated by asynchronous execution

Long tasks cannot be completed by "deleting the message". The Worker should atomically advance the state corresponding to `job_id` to `SUCCEEDED` or `FAILED`, save the result position or error code, and publish a `VideoTranscoded` if necessary. Otherwise, the caller has no way to query - the message is gone and the status is gone.

## Four common mechanisms

| Mechanism | Who processes a message | Whether to retain history for a long time | Suitable for scenarios | Main costs |
|---|---|---|---|---|
| Work Queue | A Worker in the same Consumer Group | Usually only for a short time | Image processing, email sending, background tasks | Retry, Lease, Poison Message |
| Pub/Sub | Each Subscription is processed once | Depends on the product | One business fact drives multiple downstream | Isolation of slow Subscription, Fan-out cost |
| Replayable Event Stream | Each Consumer Group maintains its own Offset | Usually longer | CDC, analysis, Derived View, Replay | Partition, Offset, storage and sequence management |
| Persistence Workflow | Multiple steps promoted by workflow engine | Save complete execution history | Multi-step long transactions, timers, manual approval | State modeling and platform complexity |

### Work Queue：Competing Consumers

Multiple workers compete for the same batch of tasks, and only one worker needs to complete each task. Broker receives ACK after successful processing; unacknowledged tasks that have timed out will become visible again. A typical example is "Generate thumbnail image for object `image_123`".

Do not use a shared queue to carry multiple business actions that should be independent of each other. If the email consumer confirms `OrderPaid`, the analysis consumer will never see it again - this requires an independent Subscription.

### Pub/Sub: Each Subscription is consumed independently

Producer publishes `OrderPaid`, and inventory, notification, and analysis each have their own Subscription and Offset. One Subscription backlog will not block another, but the platform must retain messages or advance offsets for each Subscription separately.

When adding a new Consumer, you must think clearly in advance whether you want historical events: whether to only receive new events after registration, or to start replaying from an earlier Offset. The latter is actually closer to Event Stream.

### Event Stream：Log + Partition Offset

Event Stream appends records to Partition, and Consumer uses Offset to record its own progress. It can be replayed at any time during the retention period, so it is ideal for rebuilding search indexes or derived views. Throughput is expanded by adding Partition, but the same Partition is usually processed by only one instance in the Consumer Group.

Partition Key determines both parallelism and order bounds:

- `post_id`: The creation, editing and deletion of the same post are in order;
- `user_id`: The operations of the same user are in order, but the big V will become a hot spot;
- Random Key: The distribution is the most even, but the local order in the business is lost.

### Workflow: Explicitly arrange long-term status

When a task contains multiple steps, timed waiting, compensation and manual intervention, just using a list of Topics will cause "which step to proceed now" to be scattered among several services. For example, when making a travel reservation, you need to lock the flight, book the hotel, and collect the payment in sequence. If you fail in the middle, you have to compensate for the completed steps one by one. Persistence Workflow keeps status, timers, and retry strategies in one place.

But Workflow is not a distributed database transaction. Compensation is just a new business action (such as a refund), and it cannot be treated as if the outside world has never seen the original transaction.

## Push or pull

| Mode | Advantages | Risks | Suitable scenarios |
|---|---|---|---|
| Broker Push | No overhead of idle polling, simple access | Current limiting and re-investment are required when the receiver is overloaded | Webhook, lightweight subscription |
| Consumer Pull | Consumer controls the batch and rate by itself, and Backpressure is naturally established | Offset and polling logic must be maintained | High throughput Worker, Event Stream |

Webhooks themselves are also an asynchronous boundary. The sender should sign, set a timeout, and press backoff to retry; the receiver should quickly verify and persist, and then put it in its own queue for slow processing, rather than letting the Webhook request wait for the entire business process to complete.

## Use Broker or database task table

Database task tables are not "low-level". It tends to be an easier starting point when these conditions are met:

- The amount of tasks is not large, and there are only a few Consumers;
- Business data and tasks must be submitted in the same local transaction;
- No need for multi-day event retention, large-scale Pub/Sub or cross-team data flow;
- Can use `SELECT ... FOR UPDATE SKIP LOCKED` to add lease fields and indexes to grab tasks safely.

Wait until you really need high throughput, multiple subscriptions, long-term retention, replay by Partition, or cross-language platform capabilities, then use a dedicated Broker. The two can also be combined: the Outbox table is written within the transaction, and then published to the Broker by Relay.

## What should be included in the message contract?

A message envelope that facilitates operation and maintenance usually looks like this:

```json
{
  "event_id": "evt_01J...",
  "event_type": "PostCreated",
  "schema_version": 2,
  "occurred_at": "2026-08-13T18:00:00Z",
  "producer": "post-service",
  "aggregate_id": "post_42",
  "aggregate_version": 7,
  "trace_id": "trace_abc",
  "payload": {}
}
```

- `event_id`: remove duplicates and track a certain release;
- `aggregate_id`: Routing and local order;
- `aggregate_version`: Identify out-of-order or expired updates;
- `schema_version`: Compatibility evolution;
- `occurred_at`: The time when the fact occurred - **cannot be used as a reliable sequential version**, the clock will drift;
- `trace_id`: Connect the synchronous entry and the subsequent asynchronous stage.

Whether to put the ID or the complete Snapshot in the message depends on the consistency requirements. If only the ID is put, the Consumer has to go back to the Source of Truth to get the current state, the coupling is tighter, and what it sees may no longer be the state when the event occurred; with Snapshot, it can be replayed independently, but the message is larger and involves copying of sensitive fields. A common compromise is: bring the minimum immutable data required by the Consumer to complete the action, plus an entity version number.

## Selection steps

1. First write down the business semantics: is this a Command, a factual Event, or a long process.
2. Clarify whether it is one Consumer or multiple independent Consumers.
3. Define whether to play back and how long to keep it.
4. Select the sequence boundary and Partition Key, and estimate the hot spots.
5. Define ACK timing, retry strategy, and result status.
6. Choose specific products **last** – products cannot replace the five things above.
