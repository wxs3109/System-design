# Shard Key and Routing Strategy

The sharding key determines the data distribution and also determines how many nodes each request needs to contact. We should infer from access patterns and invariants instead of just pursuing hash uniformity.

## 1. Evaluate the six dimensions of Shard Key

1. **Locality**: Can high-frequency queries be completed in a single shard;
2. **Cardinality**: Whether there are enough values ​​and whether they can be distributed in parallel;
3. **Load distribution**: Whether QPS, bytes and calculation amount are skewed;
4. **Invariant Scope**: Whether transactions, unique constraints and order fall on a shard;
5. **Stability**: Whether the object frequently changes ownership;
6. **Route Availability**: Whether the client can directly obtain the key from the request.

## 2. Common strategies

### Hash Sharding

```text
partition = hash(user_id) -> virtual partition -> shard
```

The advantage is that a large number of keys are usually evenly distributed, making it suitable for key-by-key checking. The disadvantage is that range scans and time interval queries require scatter-gather; a single super user still only falls into one partition.

### Range Sharding

```text
[A, F) -> shard 1
[F, M) -> shard 2
...
```

Suitable for scanning by time, dictionary or geographical range, and easy to split continuous ranges. The disadvantage is that monotonically increasing ID/time concentrates all new writes into the last range, creating a "hot tail". The hash prefix or time bucket can be added, but the query needs to merge more buckets.

### Directory-based Sharding

The control plane saves `tenant_id -> shard/cell`. It supports placing large tenants in independent shards, placing them in compliance regions, and migrating tenants one by one. The trade-off is that Directory becomes a critical dependency; requiring versions, caching, failsafe snapshots, and dual-homing protection.

### Composite Sharding

For example `(tenant_id, bucket)` or `(conversation_id, time_bucket)`. It can break up a single large tenant or an infinitely growing session at the cost of queries and transactions potentially spanning multiple buckets. The number of Buckets cannot be arbitrarily determined by the client and should be generated by metadata records or stable algorithms.

## 3. Case: Different data requires different Shard Key

There is no one "global shard key" for all tables in News Feed:

| Data | Common keys | Reason | Cost |
|---|---|---|---|
| Post | `author_id` or `post_id` hash | Author homepage/check part | Global timeline needs to be indexed |
| Follow edge | `follower_id` | Pull the "Who I follow" single shard | Querying the fan list requires a reverse index |
| Feed Inbox | `viewer_id` | Home page paging single shard | Super active user writing hotspot |
| Like | `post_id + bucket` | Parallel write count of popular posts | Accurate total number needs to be aggregated |

The same relationship often requires two access directions and cannot rely on scanning across all shards; a reverse index or derived view must be established, and asynchronous consistency and repair costs must be accepted.

## 4. What to do with global unique constraints?

Sharded databases typically can only enforce unique constraints within a single shard. Cross-shard username, shortcode or idempotent key options:

- Let the unique value itself determine the unique authoritative shard;
- Use independent Registry to execute condition creation;
- Pre-allocated namespace;
- Accept very low collision probability and retry in case of conflict.

You cannot build a `UNIQUE(username)` in each shard and claim to be globally unique. Registry provides strong constraints, but creates additional write paths and capacity boundaries.

## 5. Routing version

The request should carry or resolve the route version. When Shard receives an expired route, it returns a recognizable `MOVED`/new version instead of silently forwarding it infinite times. The maximum number of hops is limited internally to prevent control plane jitter from forming a forwarding loop. Write requests also require epoch/fencing during the migration period to ensure that the old owner no longer accepts writes.
